# Benchmark matrix results — Apr 2026

Run of ``scripts/benchmark_matrix.py`` on the bundled synthetic
corpus (5 documents) × 3 profiles × 2 DPIs = 30 cells. Exposed three
bugs that had shipped silently for weeks. All three are fixed; the
corresponding commits land with this document.

## Corpus

5 documents generated by
``tests/fixtures/accuracy_corpus/generate.py``:

  * ``en_business_letter`` — English prose
  * ``ru_business_letter`` — Russian prose
  * ``ru_en_mixed_memo`` — mixed rus + eng
  * ``ru_invoice_body`` — Russian invoice with units / codes
  * ``ru_dense_small`` — dense Russian body, small font

## Results before fixes (Tier A-C work as landed)

Average CER per (profile, DPI):

    profile                  DPI    avg CER
    quick_reliable           400    0.11%
    quick_reliable           300    0.21%
    default                  300    1.67%
    default                  400    1.67%
    universal_accurate       400    8.91%    ← much worse than the simpler profiles
    universal_accurate       300   16.79%    ← catastrophic

The flagship "max accuracy" preset was **80× worse** than the
fallback ``quick_reliable`` on these clean documents. Tesseract logs
surfaced three root causes:

### Bug 1 — ``-c key=value`` flags never reached Tesseract

Log showed on every run:

    [tesseract] Can't open -c preserve_interword_spaces=1
    [tesseract] Can't open -c tessedit_do_invert=0

OCRmyPDF's ``tesseract_config`` kwarg forwards its list as *configfile
names* positioned AFTER the input file. Tesseract's ``-c`` flags
must go BEFORE the input file in the options slot, not after. So
each ``"-c preserve_interword_spaces=1"`` string we emitted was
being interpreted as a filename to open — Tesseract failed, logged
the error, and ran OCR without any of our ``-c`` settings.

**Fix:** write a real Tesseract config file (space-separated
``key value`` pairs, one per line, no ``=``) into the job's workdir
and pass its absolute path via ``tesseract_config``. See
``_build_tesseract_config_file`` in
``src/application/ocrmypdf_integration.py``. This is what Tesseract's
configfile slot actually accepts, and the flags now take effect.

Char whitelist / blacklist (which went through the same broken
path) are now also folded into the same config file.

### Bug 2 — user-patterns contained invalid ``№`` lines

    [tesseract] Error: failed to insert pattern '№\d\d\d'
    [tesseract] Error: failed to insert pattern '№\d\d\d\d'
    [tesseract] Error: failed to insert pattern '№\d\d\d\d\d'

Tesseract's user-patterns grammar accepts digit / letter / punct /
literal meta-characters, but the non-ASCII ``№`` literal was
rejected by its parser. The patterns were silently dropped.

**Fix:** removed the three ``№…`` lines from
``resources/tessdata/user-patterns.rus``. Every other pattern
(ИНН / ОГРН / СНИЛС / dates / times / phone numbers) was accepted
without issue.

### Bug 3 — ``universal_accurate`` preprocessing over-tuned

    [tesseract] lots of diacritics - possibly poor OCR

Surfaced only on ``universal_accurate`` runs. Sauvola(window=25,
k=0.2) + CLAHE(clip=3.0) + background blur-division + border removal
stacked up and amplified sub-pixel noise into phantom diacritics on
thin strokes. The ~95 % mean_confidence Tesseract reported was
CONFIDENT-BUT-WRONG: high confidence on the wrong glyphs.

On every single Russian document the profile landed CER of 6-29 %;
on the English one it was 0.37 % — close to the simpler profiles
but still the worst of the five cells.

**Fix:** retune ``_build_universal_accurate`` in
``src/application/profile_manager.py``:

  * ``binarization``: Sauvola → OTSU. Global, deterministic, safe on
    clean and moderately-noisy input. Users with truly uneven scans
    still pick ``low_quality_scan`` (which keeps Sauvola + aggressive
    NLM + adaptive threshold as its differentiator).
  * ``CLAHE clipLimit``: 3.0 → 2.0. Lower amplification stops the
    diacritic-artifact regime.
  * ``background.enabled``: True → False. The blur-division pass had
    no measurable gain on any document in the matrix. Code path is
    left intact so users with dark-gradient phone snaps can toggle
    it on in the UI.

``universal_accurate``'s distinguishing features are now on the
POSTPROCESSING side:

  * 400 DPI (vs 300 elsewhere — LSTM sweet spot)
  * border removal on (fixes table rules bleeding into text)
  * drop_low_conf_words + redact_noisy_blocks
  * adaptive_confidence_threshold
  * per_word_script_disambiguation
  * fix_cyrillic_latin_confusion

## Results after fixes

Average CER per (profile, DPI):

    profile                  DPI    avg CER
    quick_reliable           400    0.11%
    universal_accurate       400    0.15%   ← was 8.91%, -59× regression gone
    universal_accurate       300    0.18%   ← was 16.79%, -93× regression gone
    quick_reliable           300    0.21%
    default                  300    1.67%
    default                  400    1.67%

Best cell per document (lowest CER, ties broken by WER):

    en_business_letter         default             300   0.37%   1.09%
    ru_business_letter         universal_accurate  300   0.00%   0.00%
    ru_en_mixed_memo           universal_accurate  300   0.00%   0.00%
    ru_invoice_body            universal_accurate  400   0.00%   0.00%
    ru_dense_small             universal_accurate  300   0.00%   0.00%

``universal_accurate`` now wins on 4/5 documents (ties
``quick_reliable`` on the fifth). Zero Tesseract warnings in the
logs — no more ``Can't open -c``, no more ``failed to insert
pattern``, no more ``lots of diacritics``.

## Lessons

1. **Always benchmark before you trust a preset.** The original
   ``universal_accurate`` tuning was based on domain intuition
   ("Sauvola handles uneven lighting", "CLAHE helps faded text",
   "background removal flattens scanner lamps"), not on measurement.
   On clean documents all three combined produced artifacts the
   simpler profiles didn't.

2. **Tesseract warnings hide real bugs.** The ``Can't open -c`` line
   scrolled past in every single CI run for weeks. Three ``-c``
   parameters we thought were applying were silently dropped.
   Adding an assertion in CI that Tesseract runs clean (no stderr
   output matching known-bad patterns) would catch this class of
   regression.

3. **Matrix benchmarking wins over spot-checks.** The ``benchmark_
   universal.py`` single-document iteration tool couldn't have
   caught Bug 3: it doesn't compare across profiles, so a
   consistently-worse profile would just look "low but plausible".
   Cross-profile side-by-side measurement is what exposed the
   regression.

## Next steps

  * Run ``benchmark_matrix.py`` on **user's real documents** with
    hand-typed ground truth. The synthetic corpus is clean-scanner
    shape; real phone snaps and aged photocopies might reveal
    a different winner (especially ``low_quality_scan`` which we
    didn't measure here).
  * Add a CI guardrail: grep Tesseract stderr for ``Can't open``,
    ``failed to insert``, ``possibly poor OCR`` and fail the build.
